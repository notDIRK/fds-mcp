# What the FragDenStaat API can and cannot do

Findings from building a client against the FragDenStaat.de (froide) REST API.
Everything here was either **measured against the live site** or **read in the source**
— each entry says which. Measurements are dated; behaviour can change.

Baseline: `fragdenstaat.de` on **2026-09-05**, `okfde/froide@bc6c2fa` (2026-09-03),
`okfde/fragdenstaat_de@88bfbba` (2026-09-04).

German version: [FINDINGS.de.md](FINDINGS.de.md)

---

## The short answer

The API is excellent for **reading and research** and deliberately narrow for **writing**.
You can find authorities, read laws and deadlines, track your own requests, and collect
replies and attachments. You can file a new request. You **cannot** reply to an authority,
and you cannot choose the legal basis when filing.

None of this is a documentation gap. We checked.

---

## 1. You cannot send a reply to an authority. At all.

This is the limitation people will hit first, so it comes first.

`POST /api/v1/message/` looks like it should do it. It does not.

**Measured 2026-09-05**, with a positive and a negative control over the same path:

```
POST /api/v1/message/   kind="email"   → 400
  {"kind": ["Nachrichten dieser Art können nicht über die API erstellt werden."]}

POST /api/v1/message/   kind="post"    → 400
  (no "kind" error — this is the calibration; without it the first result proves nothing)
```

Both calls used a deliberately invalid `request` URI, so the serializer was invalid and
nothing was created.

**Why:** `FoiMessageSerializer.validate_kind` (`serializers.py:371`) checks against
`MESSAGE_KIND_USER_ALLOWED = [POST, PHONE, VISIT]` (`models/message.py:80`). Everything
created this way is a draft, and `/message/{id}/publish/` additionally requires
`is_postal`, i.e. `kind == post` — so `phone` and `visit` drafts can be created but never
published. That is an inconsistency in froide itself.

The message API exists to **document analogue correspondence** you received on paper, not
to send anything.

### But isn't the web endpoint just undocumented?

That was our first suspicion too. It is not.

**Measured 2026-09-05:**

```
POST https://fragdenstaat.de/anfrage/<slug>/send/message/
  with Bearer token → 302 → /account/login/
  with no auth      → 302 → /account/login/     ← identical
```

The Django view ignores OAuth tokens entirely. It is session + CSRF only. Tested with an
empty form body, so nothing could have been sent even if auth had succeeded.

We also checked whether the schema might be incomplete: it is generated by drf-spectacular
from the live router, and the registered routers in the source match the schema resources
exactly. There is no hidden surface on `/api/v1/`.

**Consequence:** any workflow involving replies needs a browser and a logged-in human.
Plan for it rather than around it.

## 2. `POST /api/v1/request/` sends immediately

There is no draft mode, no preview, no undo. `CreateRequestService.create_request()` sets
`send_now = True` for any active user and calls `message.send()` in the same request
(`services.py:200-289`). The `RequestDraft` model is not registered on the API router at
all — drafts exist only in the web UI.

**The inverse risk is real too:** `201 {"status": "success"}` does **not** prove the mail
went out. `send_now` stays `False` when the user is inactive, when the campaign hook
`pre_request_creation` sets `blocked` (active on fragdenstaat.de: triggers on
`user.is_blocked` and on young accounts with more than 10 requests per IP), or when you
pass several `publicbodies` — that creates a **FoiProject** and the requests are generated
asynchronously via Celery. Always verify with `GET /request/{id}/` afterwards.

## 3. You cannot choose the legal basis when filing

`MakeRequestSerializer` accepts exactly seven fields:

```
publicbodies  int[]     required     >1 element creates a FoiProject, not a request
subject       str       required     max 230
body          str       required
full_text     bool      optional     default false
public        bool      optional     default true
reference     str       optional     "kind:value"
tags          str[]     optional
```

There is no `law_type`. The API falls back to `publicbody.default_law`, and
`get_applicable_law()` sorts by `("-meta", "-priority")` — so you almost always get the
**combined meta act**, not the specific one.

Concrete case: for a municipality in Rhineland-Palatinate, asking under the LTranspG
(law 16) through the API silently files under "LTranspG, VIG" (law 18). The mail then
carries the meta act's `letter_start`/`letter_end` and cites the wrong statute.

**Workaround:** the web form reads `?law_type=IFG` (or `UIG`) and gets it right. Hand the
user a prefilled URL instead of filing through the API.

### There is a way to file under the specific act after all

The naive conclusion — "the API cannot do the LTranspG, use the web form" — is too
pessimistic. Two facts combine into a working path.

**Fact one: `law` is writable via PATCH.** Verified 2026-09-05 with a side-effect-free
discriminator — PATCH the field with a non-existent law URI. A writable field validates and
returns 400; a read-only field is silently ignored and returns 200:

```
PATCH /api/v1/request/379655/  {"law": ".../api/v1/law/999999/"}
  → 400 {"law": ["Ungültiger Hyperlink - Objekt existiert nicht."]}
  → the field is validated, therefore writable. Nothing was written.
```

This is not a hack. froide has a first-class feature for it: `ConcreteLawForm`
(`forms/request.py:386`) exists precisely to narrow a request filed under a **meta act**
down to one of its `combined` acts afterwards. Law 18's `combined` is `[16, 3]` — so
setting 16 is the intended operation, not an abuse.

**Fact two: `full_text: true` removes the meta act's wording from the mail.** With it, the
body becomes `text + name` and nothing else (`utils.py:213`). We checked the remaining
template: `mail_with_userinfo.txt` adds only the request number, the reply-to address, the
upload link and a law-agnostic footer ("This mail was sent through a Freedom Of Information
Portal"). **No statute is cited anywhere outside `letter_start`/`letter_end`.**

**So the full API path is:**

1. `POST /api/v1/request/` with `full_text: true` and a self-contained text that cites the
   act you want — the authority receives exactly your wording, with no meta-act boilerplate.
2. `PATCH /api/v1/request/{id}/` with `{"law": ".../law/16/"}` — the record now shows the
   specific act.

Both the mail and the record end up correct.

**Three caveats, all real:**

- `due_date` is computed **at creation** from the default act and is **not** recalculated by
  the PATCH. Here it makes no difference (laws 16 and 18 both allow one month), but where the
  acts differ in response time, the stored deadline stays wrong. Check before relying on it.
- `full_text: true` drops all six boilerplate elements at once. You must supply the statutory
  citation, the cost clause, the deadline request, the forwarding request, the electronic-reply
  request, the salutation and the closing yourself. This is worth a completeness check in the
  client rather than a memory test.
- PATCH is **less** restricted than the web form. `ConcreteLawForm` only offers the meta act's
  `combined` laws and fires the `set_concrete_law` signal; PATCH accepts any existing law and
  fires nothing. Convenient, but it means a client can quietly set an act that does not apply.
  Restrict yourself to the `combined` set.

For everything other than the legal basis, the same PATCH endpoint writes `refusal_reason,
costs, description, summary, status, resolution, tags`. Only `public` is read-only.

## 4. Your text is wrapped, and the wrapping is easy to duplicate

With `full_text: false` (the default) froide builds the mail as

```
letter_start (from the law)   e.g. "Antrag nach dem LTranspG\n\nGuten Tag,\n\nbitte senden Sie mir Folgendes zu:"
your body
letter_end   (from the law)   e.g. the statutory citation, a cost-notification request,
                              a deadline request, a forwarding request, and "Mit freundlichen Grüßen"
your name
```

So if you write your own salutation and your own closing, the authority receives both
twice. We shipped exactly that mistake once before catching it.

With `full_text: true` you get only `body + name`. Everything else — salutation, statutory
citation, deadline, closing — must be in your text. Nothing is added.

**The part almost nobody knows:** in the **web form** the same option is labelled
"Vorlage anpassen" and pre-fills the textarea with the *fully assembled* text, so you edit
rather than start from scratch (there is even a "reset to template" button). Through the
**API** you get nothing pre-filled. If you want to modify the boilerplate — to add a fee
cap, say — the web form with that checkbox is the clean path.

### Replies are not wrapped at all

A follow-up sent through `/anfrage/<slug>/send/message/` receives **no** `letter_start`,
**no** `letter_end` and **no** name. Salutation and closing are mandatory in your own text.
This is the exact inverse of the rule for the initial request, and worth encoding as two
separate checks.

The reply form is pre-filled with a skeleton that contains the placeholder character
`…` (U+2026) — and `validate_no_placeholder` rejects any text containing it. Replace the
skeleton, do not append to it.

## 5. The API validates far less than the web form

| Rule | Web form | REST API |
|---|---|---|
| subject ≥ 8 characters | yes | **no** |
| subject ≤ 230 | yes | yes |
| `slugify(subject)` ≥ 4 characters | yes | **no** |
| body ≥ 8 characters | yes | **no** |
| body ≤ 5000 characters | yes (unless `is_trusted`) | **no** |
| placeholder `…` rejected | yes | **no** |
| malformed `reference` | silently dropped | **400 "Reference not clean"** |

A client should enforce the stricter web rules anyway. Otherwise you can create requests
through the API that the web UI refuses to edit afterwards.

## 6. Prefilled form URLs break at about 4 KB

The recommended workaround for the legal-basis problem is handing the user a prefilled
form URL. It has a hard ceiling.

**Measured 2026-09-05** by bisection: **4104 bytes → HTTP 200, 4105 bytes → HTTP 400.**
Independent of other headers and identical over HTTP/1.1 and h2, so it is a URI length
limit, not a header limit. A typical 4000-character request body exceeds it after
URL-encoding.

Two-step fallback: open the form with `subject`, `law_type` and `hide_publicbody=1` only
(around 220 bytes), and let the user paste the body from a file or the clipboard.

Query parameters `MakeRequestView.get_initial()` actually reads: `subject`, `body`, `tags`,
`law_type`, `responsibility`, `jurisdiction`, `draft`, `ref` (**not** `reference`),
`redirect` (**not** `redirect_url`), `public` and `full_text` as `"1"`/`"0"`, plus `email`,
`first_name`, `last_name`. `address` and `language` are **not** read from the query.

## 7. Rate limits — and one that is not enforced

On fragdenstaat.de (`fragdenstaat_de/settings/base.py:734`), exempt for `trusted()` accounts:

| Requests | Window | | Messages | Window |
|---|---|---|---|---|
| 5 | 5 min | | 2 | 5 min |
| 6 | 6 h | | 6 | 6 h |
| 10 | 24 h | | 8 | 24 h |
| 20 | 7 d | | | |

`request_throttle` **is** enforced on the API path
(`api_views/request.py:240`, `@throttle_action((MakeRequestThrottle,))`).

`message_throttle` is **not** — `FoiMessageViewSet.create` has no `throttle_action`;
`check_throttle(..., FoiMessage)` appears only in the web views. A well-behaved client
should honour it anyway.

Per the terms of use (B.1.4), **attempting to circumvent the limits suspends the account
for one month.** Do not build retry loops.

## 8. Privacy traps

- `public: true` is the default. Everything — the full mail thread, approved attachments,
  uploaded documents — becomes publicly readable and is released under **CC0**.
- The reply form pre-fills the user's **postal address** and offers a
  "send address" checkbox. On a public request, an accidental tick is a data leak.
  Verify it is unchecked before submitting.
- Do not put third-party personal data in the body. It is public and irrevocable.

## 9. Where froide's own documentation is wrong

Worth knowing before you trust it:

- `froide/docs/api.rst` states that POST/PUT/DELETE accept **Basic Authentication**.
  They do not. `REST_FRAMEWORK.DEFAULT_AUTHENTICATION_CLASSES` (`settings.py:530`) lists
  only `OAuth2Authentication` and `SessionAuthentication`, and `fragdenstaat_de` does not
  override it.
- The same file points at `/api/v1/docs/`. That returns **404**. The interactive
  documentation is at `/api/v1/schema/swagger-ui/`.
- The scope list published on <https://fragdenstaat.de/api/> omits `write:attachment`,
  which exists in the source and the schema and is required for uploads.

## 10. OAuth pitfalls

- `ALLOWED_REDIRECT_URI_SCHEMES` is `["https", "fragdenstaat"]`. **`http://localhost` is
  rejected** — the usual local-development redirect does not work. Register both
  `https://localhost:<port>/callback` and `fragdenstaat://callback`.
- Client type `Public` forces PKCE (S256) and the client secret is stored only as a hash.
  That removes the question of where to keep a secret.
- There is no client-credentials flow for user data. Every request belongs to an account.
- Refresh tokens last **180 days**.
- **`write:request` is easy to miss and mandatory** for `POST /api/v1/message/`
  (`validate_request` calls `can_write_foirequest`) and for `PATCH /request/{id}/`, which
  needs it *in addition to* `make:request`.
- A local HTTPS listener with a self-signed certificate is a fine default for humans, but
  an automated or locked-down browser cannot click through
  `NET::ERR_CERT_AUTHORITY_INVALID`, and the login then times out. Keep a manual
  copy-the-URL fallback.

## 11. Attachments

Uploads are three-step and tus-based: create the upload
(`POST /api/v1/upload/` with `Tus-Resumable`, `Upload-Length`, `Upload-Metadata`), push the
bytes (`PATCH /api/v1/upload/{guid}/`), then attach it
(`POST /api/v1/attachment/` with the message and upload URIs). Requires `write:attachment`.

Accepted types for postal messages are `PDF_FILETYPES + IMAGE_FILETYPES` — seven PDF MIME
variants plus `image/png`, `image/jpeg`, `image/jpg`, `image/gif`. The type is detected
with libmagic from the first 1024 bytes; the file extension is irrelevant.

Since only `kind: post` messages can be published, uploads are useful for documenting
scanned letters — not for attaching files to an outgoing request.

## What we tried that did not work

Recording the dead ends, because they cost the most time:

| Attempt | Outcome |
|---|---|
| `POST /api/v1/message/` with `kind: email` to reply | 400, kind rejected |
| Bearer token against the web `send/message/` view | 302 to login, token ignored |
| Prefilled form URL carrying the whole 4-KB body | HTTP 400 above ~4104 bytes |
| `fds-mcp login` with the HTTPS localhost listener in an automated browser | certificate interstitial cannot be passed, timeout after 300 s |
| Filing under a specific act through the API in one call | silently filed under the meta act — but see §3: `full_text: true` plus a follow-up PATCH does work |
| Registering `http://localhost/callback` as a redirect URI | rejected by the scheme allowlist |

## What we got wrong along the way

For calibration — these were our own errors, not the platform's:

- We first claimed status, resolution, tags and the legal basis could only be set in the
  web UI. Wrong: `PATCH /request/{id}/` writes all of them.
- We first attributed the message-kind restriction to the `OnlyPostalMessagesWritable`
  permission. Wrong: that class only implements `has_object_permission`, which DRF does not
  call on `create`. The actual gate is `validate_kind`.
- We first published a minimal scope set without `write:request`. Every
  `POST /api/v1/message/` would have failed.
- We wrote our own salutation and closing into a request body with `full_text: false`,
  which duplicates what the law template already provides.
- Our URL-length check re-implemented the URL instead of measuring the one actually built,
  and was 18 bytes short — a window where the test passed and the server returned 400.
- We concluded "the API cannot file under a specific act" and stopped there. It can, via
  `full_text: true` plus a PATCH — and froide even has a dedicated feature for the second
  half. The lesson is the general one: "the obvious call does not support X" is not the same
  as "the API cannot do X". Look for the second step before declaring a limitation.
